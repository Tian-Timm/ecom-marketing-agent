## PRD 建议结构

### 1. 项目摘要

- 项目解决什么问题。
- 面向什么角色。
- 当前 Demo 能完成什么。
- 一句话架构判断。

### 2. 问题与风险

- 设计师手动套版耗时。
- 价格低于底线。
- 广告禁用词。
- Logo 和尺寸规范。
- 纯生图模型导致产品变形和中文失真。

没有调研证据的行业数字要标注为项目假设或案例观察。

### 3. 产品目标与非目标

目标：

- 在出图前阻断业务红线。
- 对语义风险进行补充判断。
- 使用确定性代码生成稳定图片。
- 将结果回写飞书。

非目标：

- 不做开放式文生图。
- 不让模型自行修改价格。
- 不推断缺失业务字段。
- 不代替最终人工品牌审核。

### 4. 用户流程

```text
飞书任务
→ 字段规范化
→ 确定性规则
→ DeepSeek 语义复核
→ 通过则 Python 组装
→ 图片附件与状态回写
→ 前端展示
```

### 5. 输入与输出

输入：

- 商品资料表。
- 营销任务表。
- 规则文件。
- 品牌模板和产品素材。

输出：

- 审查状态。
- 违规原因。
- 语义复核摘要。
- PNG 营销图片。
- 飞书图片附件和链接。
- 输入指纹、处理版本和时间。

### 6. 规则与 Agent 边界

说明：

- 确定性规则负责硬性红线。
- DeepSeek 负责语义风险。
- 不稳定结论进入人工复核。
- Python 只组装通过任务。
- 前端只展示服务端结果。

这里可以写实现边界，但不要把这些技术说明放到前端主要体验中。

### 7. 系统架构

展示模块关系：

- Base 数据源
- 数据规范化 Skill
- 合规审查 Skill
- DeepSeek
- Python 图层组装
- 飞书 OpenAPI
- Vercel API
- Dashboard

### 8. 异常与安全设计

- 缺失字段不推断。
- 模型异常不默认放行。
- 写接口需要管理员口令。
- 每次最多处理 3 条待审查任务。
- 固定 Base，不接受任意 Token。
- 图片代理限制为固定 Base 附件。
- 输入指纹避免重复上传和回写。

### 9. 评测与证据

引用模块 05 的真实数据：

- 10 条评测集。
- 60% 边界异常。
- 10/10 状态一致。
- 6/6 异常检出。
- 10/10 规则码一致。
- 真实端到端耗时。
- 真实飞书任务 ID。

明确说明样本规模有限。

### 10. 当前限制与下一步

如实写：

- 模板数量有限。
- 评测集规模小。
- 语义复核尚未覆盖所有广告法规表达。
- 线上写操作只面向管理员。
- 尚未实现通用多品牌模板管理。

## 简历逐条核对

重点检查：

1. “从飞书多维表格读取商品数据”是否已在生产 Demo 实时完成。
2. “确定性规则与 DeepSeek API 双重校验”是否有真实证据。
3. “10 项规则以 Skill 形式封装”是否与实际规则文件和测试一致。
4. “上传飞书云盘并回写状态”是否有真实附件回写证据。
5. “单图端到端耗时小于 30 秒”是否由本次真实测试支持。
6. “信息准确率 100%”是否应该改成更准确的“任务状态一致率 100%”。

允许适度前瞻，但尚未实现的内容必须满足：

- 已经有明确模块和执行计划。
- 不冒充已上线结果。
- 面试时可以明确说明当前阶段。

## 修改规则

- 先输出 PRD 修改提纲和逐节修改说明。
- 用户确认后再写入飞书。
- 修改后重新读取文档核对。
- 不删除原有有价值的需求背景和 Badcase。
- 不重复粘贴两个相同链接。

## 验收标准

- PRD 能在 3 分钟内让面试官理解产品价值、架构判断和真实证据。
- 简历中的每个结果都能在 PRD 或 Demo 找到证据。
- 没有把计划能力写成已经上线的事实。
- 不使用大段中英混杂表达。
- 文档标题自然，不包含“猹馆项目日志”。
